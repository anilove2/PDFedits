Privacy by architecture

Your file never leaves the tab.

Most “free” PDF tools upload your document, process it on a server, then keep a copy for a while. PDFEdits has no such step: the file is read, edited and written back inside this browser.

How it works

Three steps, one device.

  1. 01

    Drop a file

    The browser reads it into this tab. No network request, no progress bar pretending to be one.

  2. 02

    Work on it

    Crop, merge, reorder, rotate, delete. Every change happens in memory, on your machine.

  3. 03

    Save it

    Download straight from the tab. The only copy that exists is the one you saved.

Questions

Fair questions.

If something is missing here, it's a gap worth fixing.

Are my files really never uploaded?

Correct. PDFEdits has no upload path: the browser opens the file, the tab processes it, and the result is written back to your disk. There is no server endpoint that accepts a document, so there is nothing to intercept, retain or breach.

Do I need an account?

No. There is no sign-up, no email gate and no verification step. The toolkit is ready as soon as the page loads.

Does it work offline?

After the first visit, yes. The app caches itself, so later edits keep working with no connection — and never depend on our uptime.

Is there a file size limit?

Only what your device can hold. Very large scans take longer because the work happens on your CPU rather than a server farm — that trade is the point.

What about scanned PDFs and OCR?

Text-based PDFs work today. OCR is on the roadmap and will also run locally; it is the slowest thing to do well in a browser, so it ships after the organiser tools.

When does it launch?

Merge, split, delete, arrange, rotate and crop come first. Everything marked In build is next in the queue; the rest follows in the order shown.
